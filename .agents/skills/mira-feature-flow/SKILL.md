# Mira Feature Flow

Проводи идею через короткий продуктовый фильтр, а затем — при подтверждении пользователя — через дизайн, реализацию и проверку. Не превращай небольшую задачу в большой документ.

## Режим работы

Определи намерение пользователя:

- Если пользователь принёс идею или спросил «что добавить», начни с этапов 1–3.
- Если он явно сказал «приступай», «внедри» или уже утвердил решение, не проси повторного подтверждения: кратко зафиксируй допущения и продолжай с этапа 4.
- Если запрос только на анализ, не изменяй код.
- Если запрос только на исправление понятного дефекта, используй сокращённый путь: контекст → реализация → проверка.

## 1. Зафиксировать идею

Сформулируй одним предложением:

> Для [пользовательницы] в ситуации [контекст] Mira помогает [результат] с помощью [механика].

Если важной информации не хватает, задай не больше трёх вопросов. Если безопасное допущение очевидно, обозначь его и продолжай.

## 2. Прожарить идею

Проверь:

1. Какая реальная проблема решается?
2. Как пользовательница решает её сейчас?
3. Почему эта функция должна быть в Mira?
4. Какой вред возможен: тревожность, ложная медицинская уверенность, перегрузка, утечка чувствительных данных?
5. Можно ли проверить ценность меньшим решением?
6. Какие данные нужны и зачем?

Вердикт должен быть одним из трёх: `делать`, `проверить прототипом`, `не делать сейчас`.

## 3. Продуктовый gate

Оцени по шкале 0–2:

- ценность для пользовательницы;
- частота проблемы;
- соответствие стратегии Mira;
- доверие и медицинская безопасность;
- стоимость реализации, где 2 означает низкую стоимость.

Сумма 8–10 — P0/P1, 5–7 — P2 или прототип, 0–4 — backlog. Это ориентир, а не автоматическое решение.

Перед реализацией сформулируй:

- основной пользовательский поток;
- главный показатель успеха;
- минимальный объём первой версии;
- что сознательно не входит в неё.

## 4. Создать короткую спецификацию

Для существенной функции создай `docs/features/<slug>.md` по шаблону
`docs/features/_TEMPLATE.md`. Для небольшой правки достаточно краткого плана в задаче.

Спецификация должна содержать только: цель, пользовательскую историю, UX-поток, данные, состояния, безопасность, аналитику и критерии приёмки.

## 5. Реализовать

Перед изменениями прочитай `docs/PROJECT_MAP.md`, затронутый route и связанные domain/API-модули.

Подключай специализированные навыки только по необходимости:

- `$mira-product-strategist` — продуктовые решения и приоритеты;
- `$mira-ux-ui-designer` — новый или существенно изменённый интерфейс;
- `$mira-frontend-implementer` — изменения React/Next.js;
- `$shadcn-mcp-ui` — когда действительно нужен компонент shadcn;
- `$browser:control-in-app-browser` — визуальная проверка пользовательского потока;
- `$github:yeet` — только по явной просьбе закоммитить или опубликовать.

Не менять Today, авторизацию, модель данных или медицинскую логику «заодно».

## 6. Проверить и передать

Проверь пропорционально риску:

- пользовательский сценарий и состояния без данных;
- mobile-first интерфейс на русском языке;
- отсутствие диагностических обещаний;
- тесты domain-логики при изменении расчётов;
- `git diff --check` и подходящие lint/test/build.

В финале сообщи: что изменилось, что проверено, что осталось, как открыть результат. Не утверждай, что код опубликован, пока push/deploy не подтверждены инструментом.

## Хранение решений

- Стабильная продуктовая рамка: `docs/PRODUCT.md`.
- Идеи и приоритеты: `docs/BACKLOG.md`.
- Утверждённые функции: `docs/features/<slug>.md`.
- Правила процесса и инструментов: `docs/WORKFLOW.md`.

Не дублируй одну идею во всех файлах: backlog содержит ссылку на отдельную спецификацию после её создания.

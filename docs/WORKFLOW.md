# Как работать с Mira через Codex

## Самый простой вход

Напишите:

> Идея для Mira: …

Codex автоматически использует `$mira-feature-flow`:

```text
Идея
  ↓
Прожарка: проблема, риск, более простая проверка
  ↓
Продуктовый gate: ценность, стратегия, безопасность, стоимость
  ↓
Короткая спека и подтверждение объёма
  ↓
UX → код → данные
  ↓
Проверка в браузере → commit/PR → production
```

Слова «внедри», «приступай» или «подтверждаю» разрешают перейти к реализации в рамках уже согласованного решения. Commit, push, merge, миграция и production deploy выполняются только по явной просьбе.

## Где что хранится

- `docs/PRODUCT.md` — стабильная продуктовая рамка.
- `docs/BACKLOG.md` — единый список идей и приоритетов.
- `docs/features/` — спеки только для утверждённых существенных функций.
- `AGENTS.md` — обязательные правила работы Codex в репозитории.
- `.agents/skills/mira-feature-flow/` — повторяемый процесс от идеи до QA.

## Нужные skills

Постоянное ядро:

1. `$mira-feature-flow` — единая точка входа.
2. `$mira-product-strategist` — продукт, безопасность и приоритет.
3. `$mira-ux-ui-designer` — UX/UI Mira.
4. `$mira-frontend-implementer` — реализация и проверки.

Подключаются по ситуации: `$shadcn-mcp-ui`, `$browser:control-in-app-browser`, `$github:yeet`, `$openai-docs`, `$skill-creator`.

Не нужно вручную перечислять все skills в каждом запросе: входной skill выбирает только необходимые.

## Плагины

Минимальный набор:

- **GitHub** — репозиторий, PR и проверки.
- **Browser** — локальная и production QA.
- **Product Design** — аудит или несколько визуальных направлений.
- **shadcn MCP** — поиск и добавление UI-компонентов.

Опционально:

- **Figma** — если макеты становятся источником истины.
- **Notion** — только если roadmap уходит из `docs/BACKLOG.md`.
- **Vercel** и **Supabase** — полезны для диагностики deploy/database, если доступны как доверенные плагины.

Не подключайте Gmail, Calendar, Slack и Drive без реального рабочего сценария.

## Hooks

Проект использует два лёгких Codex hook:

- `SessionStart` добавляет короткий контекст проекта и состояние git после старта, возобновления или compaction.
- `Stop` запускает `git diff --check`; если найдены пробелы или конфликтные маркеры, Codex должен исправить их до завершения.

Hooks описаны в `.codex/hooks.json`. При первом запуске Codex попросит проверить и доверить их через `/hooks`. Они не изменяют файлы, не отправляют данные наружу и не выполняют deploy.

Lint, тесты и build не запускаются hook-ами: это сделало бы каждую задачу медленной. Их выбирает агент пропорционально риску перед передачей результата.
